 一句话解释

 ce-code-review-loop 就是一个自动循环的代码审查与修复管家：

 ▏ 正式审查代码 → 修复确定的问题 → 验证并提交 → 重新完整审查，直到最新代码明确达到可合并状态。

 它不是新的审查器。真正负责找问题的是 ce-code-review；ce-code-review-loop 负责组织多轮审查、修复、验证和收敛。

 ────────────────────────────────────────────────────────────────────────────────

 为什么需要它？

 普通代码审查通常只运行一次：

 ```text
审查代码 → 输出问题 → 结束
 ```

 但现实中，修复一个问题后经常会：

 - 暴露另一个更深的问题；
 - 影响调用方或相邻代码；
 - 引入新的错误；
 - 让之前的审查结论失效。

 所以不能用“第一轮审查通过”或“测试通过”来证明最终代码可以合并。

 完整流程

 ### 1. 先检查工作区

 循环只能处理：

 - 当前本地分支；
 - 干净的工作区；
 - 已确定的比较基线。

 它不会为了让流程能运行而：

 - 切换分支；
 - 检出其他代码；
 - 创建 worktree；
 - 操作远程 PR；
 - rebase 或改写历史。

 如果当前有未提交改动，它会直接停止，避免覆盖用户正在做的工作。

 ────────────────────────────────────────────────────────────────────────────────

 ### 2. 固定审查范围

 循环开始时记录：

 - 当前分支；
 - 起始提交；
 - 与基线的 merge base；
 - 当前工作区状态。

 之后所有审查都使用同一个比较基线。

 这样不会出现：

 ```text
第一轮审查 A 范围
第二轮审查 B 范围
最后把两轮结果混在一起
 ```

 ────────────────────────────────────────────────────────────────────────────────

 ### 3. 调用正式的 ce-code-review

 每一轮都必须通过宿主提供的技能调用机制运行：

 ```text
ce-code-review mode:agent depth:full grouping:auto base:<固定基线>
 ```

 这里有一个重要边界：

 - ce-code-review：负责选择审查者、找问题、评估置信度、给出结论。
 - ce-code-review-loop：负责验证结果、组织修复、提交并重新审查。

 循环不能自己模仿或简化正式审查。

 例如，它不能因为“这次改动不大”就只派一个普通 agent 看几眼，然后冒充完整审查。

 ────────────────────────────────────────────────────────────────────────────────

 ### 4. 验证审查结果是否可信

 收到审查结果后，不会立刻开始修改。

 它先确认：

 - 审查的是正确分支；
 - 审查的是当前 HEAD；
 - 使用的是固定基线；
 - 所需审查者都执行了；
 - 审查结果格式完整；
 - findings 和 actionable findings 对得上；
 - 审查期间工作区没有被其他人修改。

 如果证据缺失、过期或前后矛盾，这一轮不能用于修复或证明收敛。

 ────────────────────────────────────────────────────────────────────────────────

 ### 5. 把问题分成两类

 #### 机械性问题

 仓库证据已经明确说明：

 - 哪里错了；
 - 正确行为是什么；
 - 如何验证修复。

 例如：

 - 漏掉一个调用方；
 - 测试和实现约定不一致；
 - 一个状态分支没有处理；
 - 文档、类型和实现不同步；
 - 路径安全检查缺失。

 这类问题可以自动修复。

 #### 决策型问题

 修复需要选择新的产品或兼容性规则，例如：

 - 是否破坏向后兼容；
 - 采用哪一种迁移策略；
 - 应该改变哪个产品行为；
 - 是否接受某项安全或发布风险；
 - 两种合理设计中应该选哪一种。

 循环不会替用户猜答案。

 它可以先提交互不相关的机械修复，然后用 Non-converged 报告决策阻塞项。

 ────────────────────────────────────────────────────────────────────────────────

 ### 6. 按根因组织修复

 循环不会简单地“一条 finding 一个补丁”。

 它会把共享同一根因的问题放进一个 defect family，例如：

 ```text
根因：新状态没有贯穿所有消费者

涉及：
- 状态类型
- 状态写入逻辑
- 两个读取方
- 测试 fixture
- 公共文档
 ```

 这一组作为一个修复周期，最终产生一个本地提交。

 这样避免出现五个零碎提交分别修同一个问题。

 ────────────────────────────────────────────────────────────────────────────────

 ### 7. 修复前先取得写入许可

 在任何自动修改开始前，循环会冻结：

 - 本次允许修改的精确文件；
 - 要处理的 finding；
 - 修复依据；
 - 验证命令；
 - 修改前文件内容；
 - 当前分支和 HEAD。

 然后生成一个带 lease 的 fixer packet。

 只有领取该 lease 的修复者才能编辑这些文件。

 这解决两个风险：

 1. 修复者顺手修改审查范围外的文件；
 2. 多个修复者同时修改同一个工作区。

 因此：

 - 只读分析可以并行；
 - 实际写代码必须串行；
 - 同一时间只能有一个写入周期。

 ────────────────────────────────────────────────────────────────────────────────

 ### 8. 修复者必须先声明开始

 修复者拿到 packet 后，第一步不是编辑，而是执行 cycle-begin。

 如果没有成功 begin 就出现文件修改，循环将其视为协议违规。

 它不会事后说：

 ▏ 这些改动看起来没问题，就算作循环产生的吧。

 这种“追认”会破坏回滚、并发和证据完整性。

 ────────────────────────────────────────────────────────────────────────────────

 ### 9. 只能修改授权文件

 修复者只能改 fixer packet 中列出的文件。

 如果发现必须修改额外文件，需要：

 1. 在修改前提出 scope expansion；
 2. 结束当前 lease；
 3. 重新验证扩大后的范围；
 4. 创建新的授权周期。

 不能先改完，再补报范围。

 ────────────────────────────────────────────────────────────────────────────────

 ### 10. 验证修复

 编辑完成后，循环会：

 - 检查完整 diff；
 - 确认没有额外文件；
 - 运行预先授权的验证命令；
 - 为每条命令记录明确的通过或失败结果；
 - 封存最终文件字节和权限模式。

 验证结果不能只写：

 ```json
{ "status": "passed" }
 ```

 它必须保留原来的检查清单，并逐项提供结果：

 ```json
{
  "status": "passed",
  "checks": [
    "bun test tests/example.test.ts",
    "bun run release:validate"
  ],
  "results": [
    {
      "check": "bun test tests/example.test.ts",
      "status": "passed"
    },
    {
      "check": "bun run release:validate",
      "status": "passed"
    }
  ]
}
 ```

 只要一项失败，总状态就不能写成 passed。

 ────────────────────────────────────────────────────────────────────────────────

 ### 11. 成功就创建本地提交，失败就恢复

 如果验证通过，循环会创建一个本地提交，例如：

 ```text
fix(review): validate review receipt identity
 ```

 提交前后还会检查：

 - 提交的父提交是否正确；
 - 提交是否只包含授权文件；
 - 文件字节和执行权限是否与封存结果一致；
 - Git hook 有没有偷偷加入或修改文件；
 - 提交后工作区是否干净。

 如果验证失败，则只恢复本周期明确拥有的改动。

 它不会使用宽泛的 git reset --hard 清理整个工作区，因为那可能删除用户或其他进程的工作。

 ────────────────────────────────────────────────────────────────────────────────

 为什么每次修复后必须重新完整审查？

 因为旧审查只证明旧 HEAD 的状态。

 一旦创建修复提交：

 ```text
HEAD-A → 修复 → HEAD-B
 ```

 针对 HEAD-A 的零发现、审查者覆盖和 Ready to merge 结论全部失效。

 所以必须重新运行正式审查：

 ```text
HEAD-B → 新的完整 ce-code-review
 ```

 即使：

 - 测试全部通过；
 - finding 数量下降；
 - 只改了“一点点”；
 - 修复看起来非常明显；

 也不能跳过这一步。

 ────────────────────────────────────────────────────────────────────────────────

 最终怎样才算成功？

 必须同时满足：

 1. 最新 HEAD 接受了一次全新的完整 ce-code-review。
 2. 审查结果明确为：
    ```text
Ready to merge
    ```
 3. actionable_findings 为空。
 4. 所有必需审查者都完成。
 5. 没有决策型阻塞项。
 6. 审查期间代码没有变化。
 7. 工作区仍然干净。
 8. 最终项目验证通过。
 9. 最终验证没有再修改文件。

 这时输出类似：

 ```text
Code review loop converged
Branch: feat/example
Base: abc123
Final HEAD: def456
Review waves: 3
Remediation commits: 2
Final ce-code-review: Ready to merge, no actionable findings
Verification: passed
Residual advisories: none
 ```

 ────────────────────────────────────────────────────────────────────────────────

 什么情况下返回 Non-converged？

 常见原因：

 - 工作区一开始就不干净；
 - 审查结果格式损坏；
 - 必需审查者没有完成；
 - 审查对应了错误的 HEAD；
 - 有产品或兼容性决定需要用户处理；
 - 修复验证失败；
 - 其他进程修改了分支或工作区；
 - 修复者修改了未授权文件；
 - Git hook 改变了已验证内容；
 - 同一问题反复出现或在多个状态之间振荡；
 - 工作单元额度耗尽；
 - 正式 ce-code-review 无法通过宿主调用。

 Non-converged 不等于所有工作都被撤销。已经验证并提交的独立机械修复会保留，报告会说明：

 - 已完成哪些提交；
 - 还剩哪些问题；
 - 为什么不能宣布可合并；
 - 下一轮应该从哪里继续。

 ────────────────────────────────────────────────────────────────────────────────

 max-work-units 是什么？

 它是防止无限循环的熔断器，不是质量标准。

 默认：

 ```text
max-work-units:16
 ```

 用户可以设置任意大于等于 2 的整数，没有上限。

 以下各消耗一个工作单元：

 - 一次完整审查；
 - 一个 defect-family 修复周期。

 即使某一轮因为验证错误被丢弃，也消耗一个单元。

 达到上限不代表完成，只代表停止并报告：

 ```text
Non-converged
 ```

 最后一个允许的单元如果刚好完成最终门禁，仍然可以成功。

 ────────────────────────────────────────────────────────────────────────────────

 它不会做什么？

 循环不会：

 - 推送代码；
 - 打开 PR；
 - 切换分支；
 - 创建 worktree；
 - rebase；
 - amend；
 - squash；
 - 猜产品决定；
 - 用普通 agent 冒充正式审查；
 - 并行运行多个写入修复者；
 - 把未经授权的改动追认为自己的工作；
 - 因为测试通过就宣布可以合并。

 完成后，推送和开 PR 由用户或 ce-commit-push-pr 负责。

 最简单的心智模型

 可以把它看成一家有严格交接制度的维修厂：

 1. 检查员 ce-code-review 找问题。
 2. 总管 ce-code-review-loop 验证检查报告。
 3. 总管一次只签发一张维修单。
 4. 维修员只能修维修单列出的部位。
 5. 修完后按维修单逐项检测。
 6. 通过后封存并创建一个本地提交。
 7. 换一名检查员重新检查整辆车。
 8. 只有最终检查明确写着“可以交付”，才算完成。

 核心原则：

 ▏ 修复不是完成；测试通过也不是完成。只有最新代码经过新的完整正式审查，并且在不再变化的状态下明确达到 Ready to merge，才算真正收敛。
