SPEC

更快的文档审查循环协议

把重复文档审查拆成有上限的证据轮次，严格控制指纹、快照、修复范围和最终收敛条件。

loop-protocol.md 更新于 2026-08-11 ~8 分钟阅读
要点

这套协议把反复审查变成有上限、可追踪的证据轮次：ce-doc-review 负责审查本身；循环负责准备覆盖、按缺陷家族修复、控制快照，以及判断是否真正收敛。

四个基础原语

下面四个原语全部通过技能自带的 scripts/loop-state.mjs 和标准 Node 运行时执行。每个操作只运行一条 argv 命令，并在命令之外解析单个 JSON 结果；不能用 shell 管道、重定向、命令替换、回退运算符或 GNU 专用工具临时拼装替代方案。

指纹必须真的算出来

执行 node "$SKILL_DIR/scripts/loop-state.mjs" fingerprint --path "<path>"。返回的 sha256 是文件原始字节的 64 位小写十六进制 SHA-256。绝不能写一个没从该结果中读到的摘要。需要指纹但 helper 无法运行时记 unavailable；还没走到指纹步骤就结束时记 not_reached。

原语做法失败时
一次性快照与运行状态执行 node "$SKILL_DIR/scripts/loop-state.mjs" init-run。helper 安全创建全新的私有状态根、per-run 目录、run-state.json 和快照目录，返回 run_id、run_dir、state_path、snapshot_dir。它拒绝符号链接或非当前用户拥有的托管目录，把目录权限修复为 0700，把状态文件设为 0600，并且绝不复用已存在的运行目录。无法创建或验证时返回 Non-converged；不能退化成在产品目录或产品路径上原地审查
目标解析执行 node "$SKILL_DIR/scripts/loop-state.mjs" resolve-target --product "<product>"。helper 使用 Node 的 fs.realpathSync，要求目标是现存普通文件，并返回 realpath、dev、ino、mode 和 sha256。符号链接产品路径会写穿到物理目标，但链接本身保持不变。目标不存在、不是普通文件或无法安全解析时保持未收敛
提交执行一条 argv helper 命令：node "$SKILL_DIR/scripts/loop-state.mjs" commit --product "<product>" --validated "<validated>" --expected-fingerprint "<sha256>" --expected-realpath "<realpath>" --expected-dev "<dev>" --expected-ino "<ino>"。helper 在同一进程中重新解析产品，比较物理目标身份和当前摘要，创建目标同目录的排他临时文件，复制已验证字节与原模式，并在原子重命名前立即再次完成全部身份和摘要检查。任何检查变化时删除临时文件、不修改产品链接或目标字节、非零退出并返回 status: concurrent_change；其他失败同样清理临时文件并返回 Non-converged

Wave 0：准备覆盖

必须在第一次调用 ce-doc-review 之前完成。

1

冻结输入快照

在运行状态中记录产品路径、原始 Markdown 字节和指纹。每次正式审查前，把这些字节写成一次性快照。审查结束时，产品路径仍必须匹配冻结指纹。收据记录的 ce-doc-review 修复在验证通过前只能存在于临时快照中。

2

盘点并分类合同

列出每条规范性陈述、明确要求、语义合同、交叉引用，以及明确命名或由机制隐含的证明义务。只有当所有项目共享同一权威来源、生命周期和证明边界时，才归为单合同；否则归为多合同。

3

建立 Contract Matrix

每个盘点项映射到一个单元格，未映射项记录为阻塞项。单元格包含稳定 ID、来源文本/章节、权威来源、写入方、读取方/调用者、表示形式、状态/转换、负空间场景、运行环境、证据/证明 ID、状态（open、proved、accepted_residual 或 blocked）以及剩余风险引用。这些槽位描述的是文档所规定的系统，不是仓库里的文件——每一项的证据都来自文档正文。单元格要边建边写进运行状态文件，这样长文档不必在 Pass 1 开始前把整个矩阵都放在上下文里。

单元格只能以两种方式关闭：用最终指纹上的证据标为 proved；或用绑定同一指纹的有效剩余风险标为 accepted_residual。

4

预留审查者覆盖（不要在这一步记名单）

Wave 0 阶段收据还不存在，所以这里不记录任何名单。第一份 ce-doc-review 调用者收据中选出的进程内名单才是权威结果，由 Pass 1 写入运行状态。不能复制或重做角色选择规则。每个已选进程内审查者都必须完成；可选跨模型同伴只提供额外信息。

5

按影响范围决定准备深度

多合同文档在 Pass 1 前建立 Change-Impact Graph、稳定纵向切片和证明义务。单合同文档先建立矩阵；当盘点或发现暴露跨合同边、相邻状态转换、运行时证明需求，或会影响邻近合同的修复时，再补充其他结构。

6

定义证据工件如何关闭

图边记录来源、目标、边类型、证据和状态；切片记录从权威到恢复的范围、所拥有的单元格/边和状态；证明义务记录目标单元格/边、方法、预期证据、结果、指纹和状态。

Remediation Neighborhood 包含已改动单元格，以及图上相连的调用者、消费者、反向分支、相邻转换、同级界面、fixture/oracle、元数据/交付门禁和有意保持不变的邻居。只有所有自有项目都已证明，或被当前指纹上的有效剩余风险覆盖，工件才算关闭。

7

维护持久运行状态

把盘点、合同分类、矩阵、图边、切片、邻域、证明义务、审查者覆盖、指纹、修复映射、剩余风险、发现台账、工作单元计数和状态，全部写进上面「四个基础原语」定义的运行状态文件。运行状态和产品文档是两个文件，无法一步原子替换，所以固定顺序：先提交产品文档，再刷新运行状态。若在两者之间崩溃，运行状态描述的是上一个指纹——下一轮开始前会重新校验产品指纹从而发现它，处理方式是重读产品文档刷新记录，绝不是把那次修复再应用一遍。最终门禁再用最终指纹验证整条记录。

默认情况下，被审查文档仍是唯一产品工件。

Pass 1：独立审查轮次

1

再次核对产品指纹

把产品路径的指纹与冻结指纹比较，然后创建内容完全相同的一次性快照。

2

调用正式技能（先看预算）

通过宿主平台可调用的技能机制运行 ce-doc-review mode:non-interactive <snapshot-path>；这是内部调用通道。工作单元预算耗尽时不能开始这一轮。通用任务、代理、内联审查或重建角色都不算正式调用。/ce-doc-review 和 $ce-doc-review 只属于面向用户的交接文本，绝不能交给 shell、终端、命令解析器或普通文本派发执行。

3

区分技能不可用与调用适配错误

可调用机制不存在或明确报告技能不可用时，返回 Non-converged 并记录 ce-doc-review: skill_unreachable。若误执行 slash/dollar 命令后收到 Unknown command 或其他命令解析错误，则记录 ce-doc-review: invocation_adapter_error；这不能证明技能未注册。两种情况都不能模仿审查引擎继续执行。

同时打印一段用户可直接运行的可复制块 /ce-doc-review mode:non-interactive <product-path>（仅 Codex 用 $ 前缀），并把信封的 Next bounded wave 换成这个交接块。这个块只用于输出，循环本身绝不能执行它。

4

验证调用者收据

收据必须包含 reviewed_fingerprint、result_fingerprint、已选审查者、已完成审查者、失败/超时/格式错误审查者、文档改动修复数量和终止状态。

名单怎么分类：只有当条目以 -codex、-claude、-grok、-cursor、-composer 结尾，或以 whole-doc- 开头时，才算可选跨模型同伴；其余一律按必需的进程内审查者处理，包括带 -reviewer 后缀的条目。

所有缺陷都按下面「两种失败类别」分流。完全没有收据的返回（包括正式技能那句裸的 Review failed: 输入门禁提示）属于进入前失败：返回 Non-converged 加 ce-doc-review: skill_unreachable 和实际输出。

5

提交前验证每个变化

调用者计算冻结快照到结果快照的精确差异，把每个变化的 hunk 按 section 归属到至少一条修复身份记录，并写入运行状态。要求：审查指纹等于冻结指纹；结果指纹等于临时快照当前指纹；产品路径仍等于冻结指纹；修复数量与条目一致；没有无归属的 hunk。

任何条件不满足，都丢弃临时快照和本轮发现，不修改产品路径——但这一轮照样消耗一个工作单元；连续第二次不一致就返回 Non-converged。全部通过后才提交产品路径、更新运行状态并删除临时快照。

6

不要重做审查引擎职责

文档分类、角色选择、审查派发、汇总、发现分层和 safe_auto 修复都由 ce-doc-review 负责；循环不能复制这些逻辑。

7

更新覆盖台账

把返回发现与 Contract Matrix 及适用的 Change-Impact Graph 对齐。如果验证后的结果字节发生变化，就按新指纹刷新或重验全部覆盖工件。旧快照上的发现、零发现结论、证明结果和剩余风险在重验前都已过期。

一次轮次失败的两种类别

它们的提交行为完全不同，必须分开判断。可选跨模型同伴失败两类都不属于：除非正式技能把它标为必需，否则只作报告。

类别触发条件提交行为
完整性失败指纹不一致、有无归属的 hunk、修复数量不符、收据缺字段、终止状态非 complete、产品路径已被改动字节不可信：丢弃临时快照和本轮发现，绝不碰产品路径
覆盖缺口selected_reviewers 里任何必需的进程内审查者没有出现在 completed_reviewers 中——不论什么原因、也不论它是否出现在 failed_reviewers 里——而上面所有完整性条件都成立可以提交已验证字节，但这一轮不是干净轮次：记入运行状态和 Reviewer coverage gaps，永远不能用来满足最终门禁

Pass 2：按缺陷家族修复

按语义原因分组，不按审查者顺序或文档位置分组。例如：权威归属、身份相等性、部分失败生命周期、调用者接线、交付门禁完整性。

1

先确认发现仍然有效

发现引用的证据必须仍出现在已验证结果快照中，章节/标题身份也必须相符。检查失败的旧发现已经过期，不能驱动修复，除非新正式轮次或聚焦证据检查再次确认它。

2

在临时快照中暂存改动

确认产品路径仍匹配最新指纹，再在一次性快照中应用循环自己负责的改动。只允许有证据支持、且保持产品行为、范围、优先级和既定决定不变的机械改动。完整记录前后差异并解释每个变化字节。

任何改变行为、优先级、产品形态、范围或既定决定的差异都需要用户决定。验证失败或产品路径并发变化时丢弃暂存快照——该周期同样消耗一个工作单元；同一家族连续第二次失败返回 Non-converged。成功后才提交产品路径。

3

建立 Remediation Neighborhood

从已改动的矩阵单元格出发，加入所有图上相连的反向分支、调用者和消费者、相邻状态转换和提交/取消边界、同级产品与操作界面、fixture 与 test oracle、元数据/文档/CI/交付门禁、本文档中关于前置计划或下游计划的任何假设，以及有意不变的邻居。

在运行状态中记录稳定 ID、完整成员、前后差异、聚焦检查、剩余风险、指纹和状态。

4

用聚焦证据关闭邻域

对照已改文档检查邻域。只有每个成员都已证明，或由当前指纹上的有效剩余风险覆盖，邻域才能关闭。

5

计数并刷新状态

一个缺陷家族周期消耗一个工作单元。随后刷新盘点、矩阵、图、切片、邻域、证明义务、审查覆盖、指纹和发现台账——按 Wave 0 第 7 步的顺序规则，在产品文档提交之后。预算耗尽时不能开始新周期。

不要因为文档变了就盲目重跑全量审查

先完成发生变化的 Remediation Neighborhood，再进入下一次全量门禁。

后续轮次

当所有已知重大问题——即置信锚点 75 或 100 的正式发现——及其邻域都已关闭后：

1

冻结新产品快照

冻结新的产品路径快照，并刷新或重验每个覆盖工件。

2

检查受影响切片和邻居

对受影响切片和图上相连的邻居进行聚焦证据检查。这些属于邻域证据，不是正式审查轮次。

3

运行正式全量门禁（先看预算）

调用 ce-doc-review mode:non-interactive <disposable-snapshot-path>。工作单元预算耗尽时不能开始这一轮。正式子技能没有切片范围的调用契约，因此不能把局部审查说成正式轮次。

4

分类新发现并只重开必要范围

把新发现分类为：旧缺陷家族漏掉的成员、修复引入的邻域缺陷、真正的新缺陷类型，或台账已经解决的证据。只有当先前用户决定的标准化章节/标题指纹和证据重叠仍匹配时，循环才能抑制该发现；证据有实质变化就算新问题。

只重开受影响切片及图上相连邻居，关闭邻域后再跑全量门禁。

必需审查者失败或超时是覆盖缺口，不是干净轮次。瞬时故障可以重试；否则报告缺失视角并保持未收敛。

最终收敛门禁

只有一次 ce-doc-review 审查最终快照、且下面所有条件同时满足，才能宣布收敛。通常这是一轮全新的门禁审查；但当 Pass 1 一处修复都没应用时，它审的字节就已经是最终字节，可以直接充当门禁——再跑一次内容完全相同的审查不会带来任何新证据，却要付全额审查者成本。只要改动过一个字节的轮次，就永远不能充当自己的门禁。

  • 规范性盘点完整，每一项都映射到最终指纹上的 Contract Matrix 单元格。
  • 矩阵没有无法解释的适用单元格；每个单元格都是 proved，或有有效、绑定最终指纹的 accepted_residual。
  • 每条适用的 Change-Impact Graph 边、纵向切片和 Remediation Neighborhood 都已证明，或由有效剩余风险关闭。
  • 适用的负空间与运行时证明义务在最终指纹上已证明，或由用户明确接受的剩余风险关闭。剩余风险必须写明合同/证明、影响边界、负责人、到期或复审触发条件、失败关闭行为、指纹，以及它满足的具体单元格/边/切片/邻域/义务。
  • 正式调用者信封报告零重大问题。锚点 75 或 100 属于重大问题；锚点 50 只有在暴露开放合同或证明义务时才算重大。
  • 调用者收据报告零文档改动修复。
  • 正式收据选中的每个必需进程内审查者都已完成，没有失败、超时或格式错误。这些缺口不可豁免。
  • 收据中的审查 SHA-256 和结果 SHA-256 都匹配预期最终指纹和临时快照字节；产品路径逐字节不变。零文档改动意味着不需要提交。
要点

任何编辑都会使最终快照结果失效，必须重新运行最终门禁。早期快照上的零发现不代表收敛。

轮次数只用于诊断，不是停止规则。max-work-units 是熔断器：每次全局正式审查和每次缺陷家族修复各消耗一个单元。最后一个单元可以成功完成最终门禁；如果额度先耗尽，则返回 Non-converged，列出开放合同、缺失视角、待审修复邻域和精确的下一轮范围。
